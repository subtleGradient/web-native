Topic Transcript Archive Spec

Specification for standalone topic transcript pages rendered by the shared web-native chat components.

Privacy Boundary

This spec is intentionally generic. It must not include private transcript excerpts, real private topic titles, real tool queries, real message text, real citations, or paths that reveal private conversation content. Examples in this document are synthetic placeholders.

The web-native repository may define reusable markup contracts, rendering behavior, validation rules, and release process. It must not become a storage location for private chat archives.

Goal

Archived AI conversations can be split into readable standalone topic pages. Each topic page preserves the raw current-topic messages while replacing earlier topic history with a compact summary and a link back to the previous topic page.

The generated pages should remain portable static HTML. They should work from local files and from static hosting without a build step.

Topic Boundary Rules

  • Start a new topic page when the conversation goal, subject, strategy, or working context changes substantially.
  • Do not repeat the full previous conversation in later topic pages.
  • Carry forward only a compact previous-context summary that preserves enough continuity for a reader to understand why the new topic starts where it does.
  • Include all raw messages that belong to the current topic.
  • Keep message order contiguous and preserve source turn ordering in data attributes.

File Contract

Each topic is one standalone .topic.htm file named with a stable numeric prefix and a slug.

NNN-topic-slug.topic.htm

Every topic page must use the lightweight HTML5 preamble below. The UTF-8 charset and color-scheme meta are required, not optional.

<!doctype html>
<meta charset="utf-8" />
<meta name="color-scheme" content="light dark" />
<link rel="icon" href="data:," />
<title>Synthetic Topic Title</title>

Generated topic markup should avoid wrapper tags such as html, head, body, div, and span. The renderer may use those internally in shadow DOM when appropriate.

Page Markup Contract

A topic page contains one topic-transcript element with metadata translated into data-* attributes.

<topic-transcript
  data-index=NNN
  data-topic=synthetic-topic
  data-start-message=MMMM
  data-end-message=MMMM
  data-message-count=N>
  <header>
    <h1>NNN Synthetic Topic</h1>
    <p>Messages MMMM through MMMM.</p>
  </header>
  <chat-summary
    data-scope=previous
    data-previous-href=NNN-previous-topic.topic.htm
    data-previous-title="NNN Previous Topic">
    <p>Compact previous-context summary using synthetic text.</p>
  </chat-summary>
  <chat-message data-source=MMMM-user.md data-turn=N data-role=user>
    <pre>Synthetic user message text.</pre>
  </chat-message>
</topic-transcript>

The first topic in a branch has no previous-topic link. Later topics set data-previous-href to the immediately preceding topic file and data-previous-title to that previous topic's display title.

Message Contract

  • Each message is represented by chat-message.
  • The raw message body should normally live in a nested pre so line breaks, code fences, and exact text survive generation.
  • Archive metadata stays in data-* attributes, not visible prose.
  • Useful attributes include data-source, data-turn, data-role, data-created, data-model, data-channel, data-recipient, data-content-type, data-thinking, and data-thinking-effort.
  • Visible rendering should hide archival noise such as turn numbers, model ids, and source filenames unless a future explicit inspection affordance is added.

Rendering Decisions

  • User messages render distinctly from assistant messages. The UI should show conversation structure without forcing readers to inspect metadata.
  • Assistant messages render as readable document-like content blocks.
  • Tool calls are not spoken messages. Messages with data-recipient render as tool events.
  • Tool event JSON should be parsed into readable action summaries, sections, lists, chips, and key-value rows. It should not be dumped as raw JSON when the payload is parseable.
  • Tool payload parsing must be conservative and generic. Known shapes such as search queries, opens, finds, clicks, finance lookups, weather lookups, sports lookups, and time lookups can receive readable summaries.
  • Unparseable tool payloads may fall back to escaped inline text inside a generic payload section.
  • ChatGPT-style citation tokens render as compact citation pills. Citation tokens inside inline code remain literal.
  • The transcript shell fills the full available viewport width. There is no fixed max-width cap.
  • Previous-context summaries include a compact link back to the previous topic when a previous topic exists.

Markdown-Like Body Rendering

The renderer supports a small practical subset of Markdown-like structures used in archived messages.

  • Headings up to level four.
  • Paragraphs, unordered lists, ordered lists, blockquotes, horizontal rules, fenced code blocks, and simple pipe tables.
  • Inline code, bold text, Markdown links, bare HTTP links, and ChatGPT citation markers.
  • HTML must be escaped before inline transforms to prevent message bodies from becoming executable markup.

Component Responsibilities

topic-transcript
Installs page-level styles, owns the transcript shell, and provides full-width layout.
chat-summary
Renders compact previous context and, when provided, a previous-topic link.
chat-message
Renders user, assistant, and tool-event messages from light DOM content and data-* attributes.

Release And CDN Rules

  • Topic pages must pin the shared component import to a tag or immutable revision, never to a working branch.
  • Create and push the tag before inserting it into any generated topic file.
  • Confirm the tag is visible from GitHub before the first CDN lookup.
  • Wait briefly before the first CDN lookup to avoid negative-cache races.
  • Verify the CDN response and browser module import before updating topic files.
  • If a CDN caches a fresh-tag 404, do not keep using that poisoned URL. Use a fresh pushed tag or a verified alternate CDN endpoint.

Validation Checklist

  • Every topic file has the required preamble, including UTF-8 charset and color-scheme.
  • Every topic file has exactly one component import script.
  • Every topic after the first has exactly one previous-topic link to the immediately preceding file.
  • The first topic has no previous-topic link.
  • No generated topic source introduces html, head, body, div, or span wrapper tags.
  • Message count in markup matches the expected topic message count.
  • Browser verification confirms UTF-8 decoding, component upgrade, previous-topic link rendering, citation rendering, tool-event rendering, and full-width layout.
  • Repository tests pass before a release tag is pushed.

Privacy Guardrails

  • Do not put private chat text in web-native specs, tests, docs, demos, or examples.
  • Use synthetic examples for message bodies, topic names, tool queries, citations, and previous-context summaries.
  • Do not add real local archive paths to reusable public component documentation.
  • Validation scripts may inspect private archives locally, but their durable output in web-native should be aggregate counts or generic assertions only.
  • Screenshots, fixtures, and demos committed to web-native must not reveal private transcript content.

Open Questions

  • Whether to add an explicit metadata-inspection affordance for debugging without showing archive metadata by default.
  • Whether to create a generated index page that links all topic pages in order.
  • Whether to expose custom element parts for host-page theming beyond the current shadow DOM defaults.
